## 一、先看结论：新版修掉了旧版的什么

| # | 旧版问题（真实产物复现过） | 新版做法 |
|---|---|---|
| 1 | 占位符 `【#人名_1#】` 又长又脆：1181 个里丢 99 个（8.4%），53 个括号被改坏成 `【…#]` / `[…]`，还原逻辑完全识别不了 | 短标记 `⟦12⟧`（全局序号，token 少一个量级）；一次 `re.sub` 线性还原；**容错**：`[12]`、`【12】`、`⟦ 12 ⟧`、全角数字、丢右括号都能还原；只有序号在表里才替换，正文里的 `[1]` 不会误改 |
| 2 | 还原是逐条 `str.replace`：20,000 块 / 538k 字要 **12.68s**（平方级） | 单次正则 **0.013s**（987×） |
| 3 | 专名提取乱收：`絶対友香` / `全部友香` / `一度友香` 拆成十几个"人名"，`是的`/`对不起`/`湿湿的` 也进表，遮蔽后正文直接坏掉 | 敬称前缀修剪 + 常用词黑名单 + 拟声词识别；**默认只遮人名/地名/术语表**，片假名词只进候选表（`--mask-katakana` 才遮） |
| 4 | `step3GalTranslator.py:605` 调不存在的 `LlamaCppManager.process_text`，非 GalTrans 模式 100% 失败 | 只有一条翻译路径，没有模式分叉 |
| 5 | GalTrans 产出 `_对照/_仅翻译/_原文.txt`，但清单/跳过/合并只看 `_processed.txt` → 计划永远 pending，"跳过已处理"永远失效 | **状态由文件推导**：每块落 `trans/000123.json`，有就是完成，没有就重译，不需要清单对账 |
| 6 | 无块级断点续传，中断从头来 | 块级续跑；只补跑缺的/没通过质检的块 |
| 7 | 失败也出成品：缺块就写 `【未翻译 #id】` 混进成品，下游当正常译文 | 三态语义 `ok / degraded / failed`；**strict 模式（默认）**下有任何 failed 块 → 该文件不产出成品，只写 `*_FAILED.json`（含失败块与检查明细） |
| 8 | 一块一请求，失败只会杀进程重试，没有语义重试 | `正常 → 加温 → 带反馈重译 → 行级定向修复 → 拆半重译`；漏占位符时把"漏了 ⟦3⟧，对应原句是……"写回提示词 |
| 9 | 截断（`finish_reason=length`）当成功 | 识别截断 → 放大 `max_tokens` 重取；仍截断则判 failed |
| 10 | 工作线程里直接 `root.update()` | worker 只写 Logger，GUI 用 queue 在主线程消费 |
| 11 | `kill_llama_processes()` = `taskkill /im llama-server.exe`，会误杀别人的服务 | 只按自己 spawn 的 PID `taskkill /T /F /PID`；端口被外部占用时判定为"外部服务"，退出时不动它 |
| 12 | `RegexProcessor` 用 `split('|',1)` 解析规则，含 `|` 的正则直接失效 | 改用 `pat => repl` / `pat<TAB>repl`，`|` 可以随便用 |
| 13 | 硬编码 `G:\ai-work\...` 模型路径；`temperature 0.8`；无 `max_tokens`；`--parallel 1` + KV q4_0 | 命令来自参数/配置文件（可直接抄旧 `配置库.json` 的 commands[0]）；默认 `temp 0.3`、有 `max_tokens`、KV 可配、支持多卡多 worker |
| 14 | 清洗把全角 ASCII 压半角（`！？` → `!?`）、把句子强行断行、装饰行直接删 | 标点保持原样；保留原始行结构（句子切分交给切块层）；装饰行归一成 `---` 当场景硬边界 |
| 15 | 遮蔽是裸 `replace`，会把词切开：`びっクリした` → `ビッ⟦8⟧`，模型只能把这个碎标记删掉，整块判失败（实测 112 块里挂了 2 块） | 遮蔽正则加**左边界保护**（`(?<![あ-ゖァ-ヺ])`），前面紧贴假名的不遮；自检里加了"词中假名不被拆开"用例 |
| 16 | 切块函数用字符串相加合并句子，把换行吞掉 → 多行段落变一行，行数守恒校验全部误报 | `split_long_text` 以行为单位重组，保留原始换行 |
| 17 | 上文锚点塞在 user 消息里，模型会把上文一起翻译，输出里多出一段来历不明的中文 | 上文改放 system 消息，并加"重复标题/上文回显"清洗 + 质检侧 `prompt_echo` 兜底 |
| 18 | 重试时塞回去的"上次哪里错了"提示，模型会原样吐回来混进正文；而模型还会把标题改写（`【上一次译文的问题】`→`【上次译文的问题】`），字面匹配漏过一次真的混进成品 | `strip_echo_marks()`：字面标记 + 正则兜底，出现在末尾就从标记处截断、出现在开头就只删那一行（不误删正文），自检有 3 项专测这个 |
| 18 | 改了术语表/遮蔽规则后，旧块与新切块 ID 对不上却仍被复用 → 译文错位 | 续传指纹 = 切块参数 + **遮蔽后正文 sha1**；不一致就把旧译文归档到 `trans_stale_*` |

---

| 9 | 译者把 `【#10#】` 写成 `【%102;】` 这类畸形标记，既翻不出内容、还原正则也认不出，术语永久丢失 | **三道闸门**：① 遮蔽后/翻译前 `audit_masks` 规整（`【##10】`/`【%102;】`/`⟦15⟧` → `【#10#】`，前缀匹配已知序号，认不出的残片删除）；② 译后/还原前再规整一次并记入报告；③ `ph_malformed` 质检门把写坏的块直接判 failed，反馈"请原样输出【#10#】"让译者重翻 |
| 10 | 模型偶尔把相邻两句并成一行，原文 11 行译文 10 行 → 严格 1:1 判失败，重翻 4 轮还是 10 行 | `repair_line_count()` 确定性修复：按句末把那一行拆回两行，行数对上即放行（实测 10.9 秒解决，省掉 4 轮重译） |
| 11 | 切块器对超长行"硬切"，把 `…お尻が丸見えだ。` 从中间切开，制造出原文多一行、译文永远对不上的假故障 | 切割只允许落在句末（`_HARD_END`），病态无标点长文最多放大到 3 倍上限再切，绝不切断句子 |
| 12 | 日语的「さん」被模型随机译成 小姐/女士/同学/君，同一个人前后不一致 | `gt.py polish`：9B 只判断一次"这人用哪个敬称"（女→小姐、男→君），之后**确定性替换**全部变体；实测一本 182 处 |
| 13 | 译文残留零宽字符、控制符、`【##10】` 残片、重复标点 | `clean_special()` 纯 Python 清理，产出 `合并_xxx_成品.txt` |


## 二、双模型分工（译者 + 中控）

```
         ┌─────────────────────────────┐
  原文 → │  中控（大模型）· 19092      │  不译正文，只做决定与改稿
         │  Huihui-Qwen3.8-27B @GPU1    │  ① submit_glossary：专名定名/否决假专名
         │  OpenAI 兼容 + 工具调用      │  ② submit_proofread：可疑块直接改稿（校对）
         │                              │  ③ submit_review：放行/退回判定
         └──────────┬──────────────────┘
                    │ 占位符表 / 改好的稿子
                    ▼
         ┌─────────────────────────────┐
  正文 → │  译者（小模型）· 9080       │  只管把一块日文译成中文
         │  GalTransl-v4-4B @GPU0      │  质量门：9 项自动质检 + 多轮重试
         └─────────────────────────────┘
```

为什么这么分：小模型便宜快（~2s/块），但不会“拿主意”（人名怎么统一、这句算不算错）；
27B 慢 3~5 倍但只处理少量关键决策，总成本可控。

**中控只做三事（全部走工具调用）**

| 时机 | 动作 | 不启用时 |
|---|---|---|
| 遮蔽前 | 对 49 个专名候选逐个判定 `keep`，非专名（モデル/部長/教師/イヤ…）直接剔出遮蔽表 | 启发式可能误遮，教师/部长也进占位符 |
| 定名时 | 统一中文译名（貴史→贵史、鳴沢→鸣泽、クリ→克里），结果缓存在 `terms_director.json`，续跑不漂移 | 小模型按批翻，容易出现风格不一 |
| 翻译后（可疑块） | **直接改稿**：把原文+机器译文给它，它交出修订全文（`submit_proofread`）；改完必须重新过一遍 9 项质检门，**只有变好才采纳** | 只靠小模型自己重试，往往改不动 |
| 改稿仍不过 | 退回小模型重译，并把 27B 写的“具体哪行哪个符号错了”塞进下一轮提示 | degraded 只能人工看 |

校对（改稿）的三个模式：

| 值 | 含义 | 39.9k 字 / 112 块实测 |
|---|---|---|
| `--proofread off` | 不校对，只要定名+复核 | 2.0s/块（单块翻译本身），ok 104 / degraded 8 |
| `--proofread flagged`（默认） | 只对质检报警的块改稿 | **4m53s**，ok 111 / degraded 1 / failed 0 |
| `--proofread all` | 每块都改一遍（慢但最稳） | **10m17s**（5.5s/块），ok 110 / degraded 2 / failed 0 |

`all` 值不值？用同一批切块、同温度（`--temp 0 --no-director-review`）做过 A/B：

| 指标 | off（基线） | all |
|---|---|---|
| ok / degraded | 104 / 8 | **110 / 2** |
| 中文成品字数 | 32,083 | 32,164 |
| 假名残留（成品） | 7 | **4** |
| 占位符残渣 | 0 | 0 |
| 单块耗时 | 2.0s | 5.5s（+3.5s） |

112 块里 **94 块被改动**：29 块改动 <1%（基本是同义改写），49 块 1~5%，16 块 5~20%，没有 >20% 的重写。
改动里 6 块把 degraded 修成 ok，0 块变差；另有几处是自动质检门**没抓住的真错**，值得看：

* `塊 000010`：小模型漏译了最后两句（原文 24 行→译文 20 行），**质检判了 ok**，校对把两句补回来了；
* `塊 000106`：译文开头是 `PullParser，PullParser，淫靡的汁液…`（幻觉）且漏了首句对白，校对整段改对；
* `塊 000093 / 000008`：小模型自己加了原文没有的主语（“礼子小姐高高翘起屁股”），校对按原文删掉；
* `塊 000092`：`舌の腹` → “舌腹”、`ぬちゅっと` → “「啾」地一下”，贴原文更近。

代价（也实测到了，用 `all` 前心里有数）：

* 3 块被塞进了 ASCII 双引号 `"…"`（本项目正文统一用 `「」`），排版要手工统一；
* 1 块把原文的罗马字注音 `（manzo）` 改成了假名 `（まんぞう）`，假名残留就是这么来的；
* 语气词/喘声的逗号位置被改了不少（“哈啊，哈啊” → “哈啊哈啊”），属于噪声级改动。

结论：默认 `flagged` 划算（只多花 ~1 分钟就拿到 111/1）；`all` 适合“宁可慢也要齐”的定稿轮，
不适合反复跑草稿。每万字多花 ~1.6 分钟（27B 单卡串行，约 28 块/万字 × 3.5s）。

**先启动中控**（中控不归本工具管，自己起）：


### 3.1 最省事：图形界面一键跑（接 API）

```powershell
cd F:\aiwork\galgame小说翻译\v2
.\.venv\Scripts\python.exe gt_gui.py
```

窗口里只需四步：

1. **① 原文与输出**：选你的原始 txt（可多选，乱码/广告/硬换行都不用先处理，清洗是流水线第一步）；
2. **② 模型接入** → 选「在线 API（推荐）」：
   - 预设下拉选服务商（DeepSeek / OpenAI / 硅基流动 / Kimi / GLM / 本地 LM Studio / Ollama），地址自动填；
   - 填 API Key（也可留空，改用环境变量 `GT_API_KEY`）；
   - 点 **测试连接 / 取模型** → 模型下拉自动列出，选一个（不选就用第一个）；
3. （推荐）**② 模型接入 → 中控（大模型）页签**：勾「启用中控」，预设选
   `19092 Huihui-Qwen3.8-27B`，「校对」选「只修可疑块」，点「测试」——
   它不译正文，只做定名、校对改稿和放行判定；没开 27B 就把勾去掉（自动单模型，一样能跑）。
4. 点 **▶ 开始翻译（一键）**。

接下来全自动：清洗 → 提取专名 → （中控定名/否决假专名）→ 遮蔽 → 切块 → 翻译（带质检、
中控复核、多轮重试）→ 还原占位符 → 组装三份成品 →（可选）合并 → 关服务 → 自动打开输出目录。

跑完给你一份汇总（字数/块数/降级数/失败数/耗时/吞吐）。strict 模式下若有失败块，
会问一句「是否改用允许部分成品重跑」——选是则只重译失败块。

设置（含 API Key，**明文**）存在 `v2/settings.json`，下次打开自动带回来。

### 3.2 命令行

```powershell

  --gpus 0 --chunk 400 --chunk-max 640 --context 0 -o OUT_book --merge

# 5) 连接已经在跑的服务（不自己拉进程）

# 6) 中断了？原命令再跑一次就是断点续传

python gt.py status OUT_book
python gt.py merge OUT_book
```

常用参数：

| 参数 | 说明 |
|---|---|
| `--api-base` / `--api-key` / `--model` | OpenAI 兼容端点；Key 也可用 `GT_API_KEY`；模型留空取 `/models` 第一个 |
| `--director-base` / `--director-model` | 中控（大模型）端点与模型名；不填则单模型跑 |
| `--no-director` / `--no-director-review` / `--no-director-veto` | 关中控 / 只定名不复核 / 不允许否决遮蔽 |
| `--proofread off\|flagged\|all` | 中控校对模式（默认 flagged：只改可疑块） |
| `--proofread-tries N` | 单块最多让中控改几次稿（默认 2，防烧 token） |
| `--workers` | 并发请求数（API 模式建议 2~8；本地单卡建议 1） |
| `--chunk` / `--chunk-max` | 每块目标字数 / 单块硬上限（日译中建议 300~500） |
| `--context` | 上文锚点字数（0=不给；80~120 有助于人称/语气连贯，会略增 token） |
| `--allow-partial` | 有失败块也产出成品（默认 strict 不出成品） |
| `--no-mask` / `--mask-katakana` | 关闭遮蔽 / 连片假名专名一起遮 |
| `--glossary` | 外部术语表 `{"词": {"type":"人名"}}`，强制保留 |
| `--style` | 占位符样式：`bracket`⟦12⟧ / `double`[[12]] / `hash`【#12#】 / `brace`{#12#} |
| `--dry-run` | 不调模型，验证清洗→切块→组装链路 |
| `--save-config` | 本次参数存成 json，下次 `-c that.json` 复跑 |

### 3.3 API 模式做了什么适配

* 自动补 `/v1`（`https://api.deepseek.com` → `.../v1`），本地地址不改；
* 请求体只发标准字段（`model/messages/temperature/top_p/max_tokens/stream`），
  不发 llama.cpp 专属的 `repeat_penalty` / `cache_prompt`，避免云端 400；
* 带 `Authorization: Bearer`；探活走 `/models` 而不是 `/health`；
* 429/503 自动退避重试并尊重 `Retry-After`；
* 并发多路复用同一个端点，每路仍是流式解析 + 看门狗超时。

### 3.4 单元模式：≤N token 的完整句（`--mode unit`）

块模式是「一块 400 字一起翻」；单元模式是**先把正文拆成一条条不超过 N token 的完整句**，
逐条翻、逐条查、再按原顺序装回去。切分语义对齐 `F:\aiwork\猫仔v4\猫仔AI分章器.py` 的分块器：

* 只在句末标点（`。！？!?…`）后断句，句末标点后面的 `」』）` 一起带走；
* `「」『』` 算对话边界（`「あぁ」と言った。` → `「あぁ」` + `と言った。`），
  `（）【】` **不**参与断句（`これは、礼子（れいこ）さんだ。` 不会被切成两半）；
* 单句自身就超过上限 → 整句独占一条，**绝不从句中间切**；
* 贪心打包：累计 token 尽量接近上限但不超（同 `v6_group_chunks`）；
* 纯标点/纯符号（孤立的 `？`、`……`）原样透传不送模型
  —— 实测把这种行单独发给 4B，它会开始复述系统提示词。

```powershell
# 单元模式：20 token 一条，8 条一个请求，4 个 slot 并发
python gt.py translate samples\sample_ja_full.txt -o OUT_unit `
  --mode unit --unit-tokens 20 --unit-pack 8 `
  --base-url http://127.0.0.1:9081 --workers 4 `
  --director-base http://127.0.0.1:19092/v1 --director-model qwen3.8-27b
```

流程（和块模式共用前面的清洗/专名/遮蔽/术语）：

1. 拆单元 → 打包（默认 8 条/请求）→ 多 worker 并发译；编号对不上的条目自动单条补译；
2. 27B 逐批定性（默认 8 条/批）：`ok` 放行 / `order` 用它的修正稿直接换 /
   `wrong` 带「上一次译文的问题」重译，然后复检；
3. 按「源行号 + 行内序号」装回：行数、空行、`---` 场景线与清洗后原文**严格一致**；
4. 全文终检（默认全量再扫一遍）→ 再装回 → 出成品。

| 参数 | 默认 | 说明 |
|---|---|---|
| `--mode chunk\|unit` | chunk | unit = 单元模式 |
| `--unit-tokens` | 20 | 单条单元 token 上限（完整句，超了就整句独占） |
| `--unit-pack` | 8 | 一个请求装多少条（**1 = 逐条发，实测慢 1.5 倍且失败更多**） |
| `--unit-context` | 80 | 每批带多少字上文（人称/语气连贯） |
| `--unit-check-pack` | 8 | 27B 一次判多少条（再大不提速，27B 已满负荷） |
| `--no-unit-check` | 关 | 不交 27B 定性（只留本地规则门） |
| `--final-check off\|fixed\|all` | all | 全文终检：不查 / 只查改过条目及其邻域 / 全量 |
| `--slots` | 1 | 自启 llama-server 时开 `--parallel N`，N 个请求共用一卡 |

单元模式的产物多出三样：`units.jsonl`（单元表）、`units_meta.json`（切分指纹）、
`utrans/NNNNNN.json`（单条状态）。续传就是靠 `utrans/`：切分参数变了会把旧的整目录
改名成 `utrans_stale_*`，不会错位复用。

## 五、质检门（validate.py）

每块译文过 9 道检查，任一道 fail → 该块 failed：

| 检查 | 抓什么 | fail 条件 |
|---|---|---|
| `nonempty` | 空返回 | 译文为空 |
| `prompt_echo` | 模型把提示词复读 | 命中 "系统保护占位符 / 只输出中文翻译 / 你是一个专业的日文翻译" 等特征 |
| `refusal` | 拒译/道歉 | 短文本里出现"抱歉 / 我无法 / 作为AI" |
| `line_count` | 行被合并/拆开 | 行数偏差 > 45%（> 20% 记 warn） |
| `placeholder` | 占位符丢失/凭空出现/次数不符 | 缺失或新增即 fail；次数不符 warn |
| `quote_anchor` | 对白结构 | 原文有「」而译文一个都没有 → fail |
| `kana_residue` | 没翻干净 | 译文假名占比 > 6%（> 2% warn） |
| `length_ratio` | 漏译/灌水 | 译/原字符比 < 0.18 或 > 3.2 |
| `untranslated` | 原文照抄 | 与原文逐位相似度 > 85% |
| `repetition` | 退化复读 | 连续重复行 > 3（warn）/ 去重字符率过低（fail） |

阈值集中在 `core.DEFAULT_THRESHOLDS`，可用 `-c job.json` 覆盖。

## 六、实测数据（本机：3090×2 + 3060）

### 6.1 单模型（仅译者 4B）

模型：`GalTransl-v4-4B-2601`（Q8, llama.cpp b11874, ctx 8192, q8_0 KV）

| 场景 | 结果 | 耗时 |
|---|---|---|
| 旧流程（逐句块 + `【#类别_n#】` + 无质检） | 67 块里 7 块提示词复读、1181 个占位符丢 99 个、53 个括号坏掉 | — |
| 新流程，5,985 字样本（chunk 300） | 22 块：ok 21 / degraded 1 / failed 0 | 28.3s |
| 新流程，**39,903 字真书**（chunk 400） | **112 块：ok 101 / degraded 11 / failed 0**，成品 32,048 字，占位符残渣 0 | **3m15s** |
| 中断后续跑（在 38/112 处强杀进程） | 复用 37 块，只补跑 75 块 | 3m15s → 2m20s |

吞吐 ≈ **205 字/秒**（单 3090）。11 个 degraded 里 10 个是"占位符次数不符"（同一名字的某个出现位置没写进去），
1 个是假名残留超阈值，明细在 `_report.json` 的 `bad_checks` 与 `trans/*.json`。

参考产物：`OUT_book2\sample_ja_full\`（单模型版）。

### 6.2 双模型（中控 27B @19092 + 译者 4B @GPU0）

同一本 39,903 字真书、同样 chunk 400，只换接入方式：

| 配置 | ok / degraded / failed | 假名残留 | ⟦残渣 | 耗时 |
|---|---|---|---|---|
| 单模型（仅 4B） | 101 / **11** / 0 | 11 | 0 | 3m15s |
| + 中控定名/复核（不改稿） | 105 / 7 / 0 | 19 | 0 | 5m34s |
| **+ 中控校对改稿（当前默认）** | **111 / 1 / 0** | **2** | **0** | **4m53s** |

校对改稿比“只复核”**又快又好**：报警块直接由 27B 一次改写完成，不再让小模型反复重试。
9 个块走了校对，其中 8 个从 degraded/failed 变成 ok（包括一次 failed → ok），
只剩 1 个块（13 行里 11 个占位符）27B 连改两次仍差次数 → 计 degraded，明细在 `trans/000024.json`。

三次跑之间本身有 ±3 块的随机波动，但趋势没变：**中控把 degraded 从 11 拉到 1，假名残留从 11~19 拉到 0~2**。
只要定名不要改稿：`--proofread off`，耗时回到 3 分半。

中控在真书上确实抓到了小模型自己发现不了的东西：

* `塊 000106`：开头整句变成 `PullParser，PullPars…`（小模型幻觉），复核后重译通过；
* `塊 000046/000081/000110`：把 `⟦4⟧さん` 译成"⟦4⟧小姐/友香姐"（占位符被吃掉），校对直接改回；
* 定名：`貴史→贵史`、`鳴沢→鸣泽`、`クリ→克里`；遮蔽否决：`モデル/部長/親御/変態/義兄/教師/イヤ`
  等 42 个假专名（候选 49 → 实际遮蔽 7）。

参考产物：`OUT_book10_final\sample_ja_full\`（校对版）、`OUT_book7_veto\`（只复核版）、
`OUT_ab_base\` 与 `OUT_ab_all\`（`--proofread off` vs `all` 的同块 A/B，逐块对照在 `C:\Users\Public\ab_diffs.txt`）。

## 七、已知限制

1. **术语译名靠模型**：开了中控就由 27B 定名并缓存（`terms_director.json`），没开则 4B 批量翻
   （25 条一批，失败回落单条）。不满意直接改 `terms.json` 的 `target` 再重跑：
   只改 target 不影响已翻译的块，重组装即可；改词表本身才会触发重切块（旧译文归档 `trans_stale_*`）。
2. **degraded 块会计入成品**（`--allow-partial` 时 failed 也会），明细都能查到。
3. **括号类文本**（`（）` 旁白、注释）按普通字符处理，不做语义区分。
4. **GUI 单机串行展示**，不做多机分发；多卡并行走命令行 `--gpus 0,1 --workers 2`。
5. 单个文件必须在**一次 strict 通过**后才产出成品；块数很多的巨著建议 `--allow-partial` 后人工抽查。
6. API 模式的并发上限取决于服务商限流（429/503 会自动退避，但太高的并发只是白等）；
   免费额度端点建议 `--workers 2~4`。
7. `settings.json` 里的 API Key 是**明文**；不想落盘就留空，用环境变量 `GT_API_KEY`。
8. **中控是额外开销**：校对改稿每块一次 27B 生成（实测 +3.5s/块），所以默认只对报警块做；
   `--proofread all` 很贵（+175% 总时长）。中控挂了会自动退化，已做的定名不会重来（`terms_director.json`）。
9. 中控的“遮蔽否决”会改变 `masked.txt` → 已译块作废重译。第一次开中控跑一个已有产物目录时
   会看到 `trans_stale_*`，这是预期行为，不是 bug。
